# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"IEMprove" (formerly "מחברת", Study Hub): a personal study site for a BGU semester (Hebrew, RTL UI). Lecture decks (PDF/PPTX) are converted to slides, then analysed by Claude into summaries, topics, quizzes, flashcards, glossary and notes. It also syncs with BGU Moodle (new material, announcements, deadlines, grades) and the public BGU course catalog (class groups, exam dates).

All user-facing strings are Hebrew; code and comments are English. Code commits use English messages; `עדכון תוכן: …` commits are made automatically by the server (see Auto-publish).

## Commands

```bash
npm run dev            # Express server on :5180 (node --watch) + Vite on :5173 (proxies /api and /files to :5180)
npm start              # vite build → dist/, then serve everything from the Express server on :5180
npm run build          # client only → dist/
npm run build:static   # cloud build → dist-cloud/ (client with VITE_STATIC=1 + exported data JSON)
node scripts/serve-cloud.js   # static preview of dist-cloud on :5190 (no Functions, so no sign-in / /api)
npm run seed [dir]     # import the first lectures with hand-written content from seed/content/ (default ~/Downloads)
```

Node 22 (`.node-version`). There is no test suite, linter or formatter.

On the owner's Mac the server runs permanently from a LaunchAgent (`com.studyhub.server`, log in `logs/server.log`), so port 5180 is usually already taken. After code changes, rebuild and restart it:

```bash
npx vite build && launchctl kickstart -k gui/$(id -u)/com.studyhub.server
```

Useful env vars (`.env`, see `.env.example`): `AI_PROVIDER=api|cli`, `AI_MODEL`, `ANTHROPIC_API_KEY`, `PORT`, `HOST`, `STUDY_DATA_DIR` (alternate data dir for testing), `NO_INBOX=1` (don't watch `inbox/`), `AUTO_PUBLISH=0` (don't git-push data), `MOODLE_URL`, `CLOUD_URL`, `STUDY_ADMIN_SECRET`. For local end-to-end tests of Moodle flows, `scripts/dev/mock-moodle.mjs` is a mock Moodle web service (fictional test users) to point `MOODLE_URL` at.

## Architecture

### Two deployments, one client

1. **Local server (the Mac)** — `server/index.js` (Express 5). Full feature set: upload, ingest pipeline, AI chat/practice generation, Moodle sync, catalog sync, updates/notifications, backups. Binds to `127.0.0.1` and rejects non-localhost `Host` headers and cross-site state-changing requests.
2. **Cloud site (Cloudflare Pages, `study-hub-git`)** — built from GitHub `main` with `npm run build:static`. Course material is pre-exported static JSON under `/data/*`; students sign in with their Moodle credentials. Only `/api/*` and `/data/*` run Functions (`_routes.json`):
   - `functions/api/[[route]].js` → `cloud/api.js`: auth, per-student progress/settings/deadlines/grades, ICS calendar feed, reports, and the `/api/admin/*` channel used by the Mac (Bearer `ADMIN_SECRET`).
   - `functions/data/[[path]].js` → `cloud/gate.js`: serves `/data/*` only to students enrolled in the course (filters lists, 403s other courses' files).
   - D1 database `DB`; schema is created lazily in `cloud/lib/db.js` (no migrations). Secrets `TOKEN_KEY` (encrypts Moodle tokens) and `ADMIN_SECRET` are Pages secrets; local values in `.dev.vars` for `wrangler pages dev`.

The client (`client/src`, React 19 + react-router + Vite, root is `client/`) is the same for both. `STATIC = import.meta.env.VITE_STATIC === '1'` in `client/src/api.js` switches it: in static mode `api.get('/api/…')` is rewritten via `STATIC_ROUTES` to `/data/….json`, search runs in the browser over per-course indexes, `CLOUD_API` paths go to the Functions, and anything else throws `LOCAL_ONLY`. **A new read endpoint that should also work in the cloud needs three changes:** export the data in `scripts/build-static.js`, map it in `STATIC_ROUTES`, and allow it in `cloud/gate.js`.

### Data model (`data/`, committed — it is the source of the cloud build)

- `data/courses.json` — courses. `DEFAULT_COURSES` in `server/lib/courses.js` is merged in on read (missing ones are appended); courses can also be created from Moodle enrollments, and `server/lib/catalog.js` adds `classes`/`exams` from the BGU catalog. Course `keywords`/`code` drive automatic course detection of uploads.
- `data/lectures/<courseId>-<rand>/` — one dir per item (`kind`: lecture | tutorial | homework | exam): `meta.json` (status, stage, numbering, `originalFile`), `slides.json` (per-slide text), `content.json` (AI or seed study content, shape defined by `LECTURE_SCHEMA`/`NOTES_SCHEMA` in `server/lib/prompts.js`), the original file, `deck.pdf` for PPTX, and `slides/*.jpg`. Only `slides/t001.jpg` is committed; the cloud renders slides from the PDF in the browser (pdf.js) and falls back to images only for decks over the 25 MiB asset limit.
- `data/updates.json` (feed, deadlines), `data/links/`, `data/practice/`.
- `shared/` holds code used by both the client and the cloud/Mac (group detection, the portal API client).
- Course `grading` (components, weights, "מגן" shields, min exam grade, notes) is extracted by AI in `server/lib/syllabus.js` during the catalog sync: from the public syllabus page the catalog links to, else a syllabus PDF on Moodle, else the opening lectures' slides. Re-read only when the source text's hash changes; the grades page's exam calculator starts from it.
- Private, never committed: `data/moodle.json` (Moodle token), `data/progress.json`, `data/reports.json`, `backups/`, `.env`, `.dev.vars`.

All reads/writes go through `server/lib/store.js` (atomic tmp+rename writes). Scripts in `scripts/` import it directly.

### Ingest pipeline (`server/lib/ingest.js`)

Files arrive via upload (`/api/upload`), the watched `inbox/` folder (`inbox/<courseId>/` forces the course; processed files move to `inbox/נקלטו/`), or Moodle sync. A single in-process queue runs stages `converting → rendering → extracting → classifying → analyzing → ready` (`STAGES`; labels mirrored in client `STAGE_LABELS`). Conversion uses Microsoft PowerPoint (AppleScript) or LibreOffice `soffice` for PPTX, poppler `pdftoppm`/`pdftotext` for rendering/text (`server/lib/extract.js`). Kind and lesson number are inferred from file names with the regexes at the top of `ingest.js`. Unfinished items resume on startup (`resumePending`).

**What goes on the site (the owner's rule):** only what is on Moodle. Lectures get AI study material; **tutorials don't** (the owner: a summary of a worked-examples sheet isn't worth the time – they go up as slides and files, and `aiKindOk` in `server/lib/courses.js` is the one rule: no AI for tutorials or exams, and a course's `aiKinds` can narrow it further; tutorials that already have content keep it); past exams (`kind: 'exam'`) and files marked `noAi` go up as they are – `noAi` is set automatically for scanned files (less than `MIN_TEXT` characters of text, `noAiReason: 'scanned'`) and by hand for question banks that span the whole course (`'bank'`), and `retry-ai` skips them. Generated practice (`POST /api/courses/:id/practice`) takes its style from the course's homework and tutorials (or its lectures before there are any) but may only cover topics already taught: the prompt gets a `taught_so_far` list from the lectures and tutorials on Moodle – never get ahead of the course. `meta.held` keeps an item on the Mac but out of every list (`listLectures`). **Question banks** (`server/lib/practice.js`): each lecture/tutorial/prep unit is grown to `BANK_TARGET` (200) questions in rounds of 20, each round focused on another stretch of its slides, kept in `content.extraQuiz` (checked by `checkQuiz`, near-duplicates dropped). They run on their own worker (`queueBank`) – after ingest, and for existing lessons via `POST /api/maintenance/grow-banks` – so a new lesson is published before its bank fills in; a usage limit or sign-out stops the run until the next one. Each round is written by **Claude (Sonnet, `AI_BANK_MODEL`) at night** (`BANK_CLAUDE_HOURS`, Israel time, default `1-7`, at most `BANK_CLAUDE_CAP` = 40 rounds a night, counted in `logs/bank-state.json`; a usage limit ends Claude's night) and **by Gemini at any other hour** within the share of its free daily quota not kept for lessons (`geminiRoom`; also at night once Claude's cap is used or it fails): `bankWriters()` in `practice.js` says who may write now, and the AI watch resumes the banks whenever either answers. Every CLI call is killed after 20 minutes (`CLI_TIMEOUT` in `ai.js`) so a hung call can't block a queue. Students practise in sets of 15 (`PracticeTab` in `Lecture.jsx`: unanswered, then wrong, then the rest) with "עוד 15 שאלות" at the end. A set in progress survives a refresh: `Quiz`'s `persistKey` saves the shuffled set and the place in it in localStorage (lesson practice and the course practice test). `quizCount` on lecture cards counts both `quiz` and `extraQuiz`. A question whose wording points at something on a slide ("לפי הטבלה בשקף 7", "בתרשים שהוצג") gets `showSlide` from `slideRef` in `checks.js` (run by `checkQuiz` on every new question; a slide number named in the text wins over the model's `slide`), and `Quiz` shows that slide inside the question (`SlidePeek inline`); `POST /api/maintenance/slide-refs` re-marks existing questions (and escapes their currency dollars). `fixSlide`/`matchSlide` (`checks.js`) also correct the model's slide number by text: the words of the question and its right answer (formulas left out) are compared with each slide's text, and the claim moves only when another slide matches clearly (≥ 0.4) and the claimed ±1 clearly doesn't (< 0.25, gain ≥ 0.2); questions with fewer than 6 distinct words keep their slide, a link is never dropped (image-only slides – diagrams, dashboards – have no text to match), and a slide named in the question text always wins. A question that leans on data it doesn't carry ("בנתוני שני השדות", "בדוגמת שני העובדים" – `DATA_REF` in `checks.js`) gets `showSlide` too, so the slide with that data appears inside it; `needsContext` marks questions that a reading of the whole bank (Claude, in batches) found to lean on a table, case or exercise they don't carry ("מר שמיר", "בתרגיל 2"): `markSlideRefs` keeps `showSlide` on for them whatever the wording. Open questions and flashcards have no slide field, so their context is a line in the text ("הקשר: …, שקפים …"). a question that leans on another question (`ANOTHER_Q`, "בהמשך לשאלה הקודמת") is dropped, since sets are shuffled (`checkQuiz` for new ones, `markSlideRefs` for existing ones). The question prompts carry `SELF_CONTAINED` (every question must make sense alone). `checkQuiz` also warns when under 20% of a set is `hard` (the prompts ask for a third hard, a third medium, a third easy). **Currency vs math:** `shared/currency.js` `escapeCurrency` turns every `$` that isn't part of a real formula (one line, no Hebrew inside, not opening/closing on a space, not followed by a digit) into `\$` – the client runs it before rendering (`Markdown`, `RichText`, `plainText`) and `checkQuiz` on new questions, so prices like "67$ … 1.6$" never pair up into a garbled formula.

**Exam-prep units** (`kind: 'prep'`) are lessons from an earlier semester that this one hasn't reached, imported as text only (no deck, `originalFile: null`): `node scripts/import-prep.js <courseId> <dir> "<semester>"` posts `slides-NN.txt` (+ optional `transcript-NN.txt`) per lesson to `POST /api/courses/:id/prep` → `addPrepItem`, which saves the text as `slides.json` and the transcript as `transcript.txt` (gitignored, stays on the Mac) and queues it; `prepPrompt` writes the usual study content from both. They are not counted as lessons (listed under the course's "הכנה למבחן" tab, `PrepUnits`), have no slides tab, and their quizzes and cards join the course's exam practice. The IS course's units (from its NotebookLM, semester B תשפ"ו) are held: the owner wants only what is on Moodle.

**Linear algebra** (the two Moodle courses `m66384`, `m67024`, built from other students' enrollments, `remote: true`) has `ai: true, aiKinds: ['lecture'], bank: false`: AI summary, questions and cards for lectures only – no tutorials, no homework, no question banks (`bankOk`) – so the free Gemini quota isn't spent on a course the owner isn't in. Other remote courses stay `ai: false`. Check each generated summary against the pages (the owner can't read them): the model adds illustrative examples, which are marked "דוגמה להמחשה" / "להשלמה" when they aren't in the lecturer's document. Explanations never refer to an option by its place (`unorder` in `checks.js`, run by `checkQuiz` and the prompts' `SELF_CONTAINED`): options are shuffled for the student.

### Notices read by Claude (`server/lib/notices.js`)

The course material goes to whatever `AI_PROVIDER` says (Gemini by default now), but every new **notice** is read by Claude (`generateJSON({ use: 'claude' })` → `claudeStatus()`: the API key or the logged-in CLI, model `NOTICES_MODEL`, default `claude-sonnet-5-5`, effort low): Moodle course announcements on the feed (`pendingNotices` / `setNoticeAnalysis` in `updates.js`, last 14 days, 3 tries each) and the portal's notices on students' lessons (`GET /api/admin/notices/pending` → `POST /api/admin/notices/result`; the cloud keeps them in `notice_analysis` by `noticeKey`, deduplicated across students, a NULL row's `at` counts failed tries). The reading (`NOTICE_SCHEMA`: kind, groups, room/day/time/date, headline, urgent) passes `checkNotice` – groups must exist in the course's catalog classes, room/time/date/headline may not carry digits the notice doesn't have, `urgent` only for lesson changes. It runs after every Moodle sync and every 3 minutes (cheap when nothing is waiting: no run is logged; `startNotices`, `NOTICES=0` off; `POST /api/maintenance/notices`), logged as run process `notices`. The cloud holds a portal notice's phone push for up to 10 minutes while it is unread and the Mac's heartbeat is recent (`heldNotices` in `portal.js`, first sight in `push_meta` as `ns:<key>`), so it usually goes out with Claude's headline; after 10 minutes, or when the Mac is off, it goes out in the portal's own words. `shared/notices.js` is how it's used: `forOtherGroups(text, course, mine, analysis)` trusts the reading's groups over the text heuristics, notifications (rules 6 and 7 in `notify.js`) take `noticeTitle` as the title and `noticeUrgent` as a high-priority push, `portal.js` attaches readings to the lessons (`withReadings`), and the updates page / portal card show the kind and headline. A reading (version `NOTICE_VERSION`, older ones are read again) also says which meeting it is about – `classType`, `onDate` (YYYY-MM-DD, worked out from the posting date and verified by `checkNotice`: within -10…+60 days, on the weekday and the date the text names), `repeats` (permanent), `start`/`end`. **`shared/schedule-changes.js`** turns cancellations, room changes and time changes into dated changes (`changesFrom`, `changeFor`): the site's timetable (`slotOn` / `thisWeek` / `upcoming` in `client/src/lib/schedule.js`) marks a cancelled meeting "לא מתקיים" (and shows the new room or time) until that meeting has ended, then it is the regular one again; a permanent change stays for later weeks. A permanent change that names only a weekday ("בימי ראשון … שינוי קבוע") has no `onDate`: `checkNotice` keeps `repeats` when the day is named (and sets it from wording like "שינוי קבוע" that the model missed), and `changeOf` starts it at the first such weekday from the posting date. `NOTICE_VERSION` = 3. A portal notice is anchored to its own lesson (weekday + start; no date → the lesson's next meeting after it was posted), an announcement matches by course, class type, groups, weekday and start. The cloud's class reminders (rule 4) use the same changes. The portal's own `canceled` flag counts for this week's meeting only. Without a reading everything works as before on the plain text. The `/system` page has a `notices` check from the heartbeat (`noticesState`).

### What's missing on the site (`server/lib/gaps.js`)

`siteGaps()` (sent in the heartbeat as `mac.gaps`, at most once a minute) lists lessons that are ready but lack a summary, notes, questions or cards, and the question banks' progress (`have`/`want`, lessons still below `BANK_TARGET`, Claude's rounds tonight, `lastAdded`). `shared/system-checks.js` turns it into the `gaps` check on `/system` ("מה חסר באתר") with phone alerts to the owner: a lesson missing material for more than 3 hours (once per lesson), and banks that haven't grown for 30 hours while some are below target (once a day). Exams, scanned/`noAi` files, held items and prep units are not gaps.

### The degree committee's view (owner only)

`/committee` ("מערכת הועד", nav item and route only when `!STATIC || me.owner`) lays every course's weekly meetings over each other to find hours when nobody has class (make-up lectures, tutorials, office hours). `server/lib/committee.js` keeps `data/committee.json` (published like other data): `extra` = courses the site doesn't carry (linear algebra, read from the catalog by `fetchCatalog`, refreshed every 12 hours or `POST /api/committee/refresh`) and `lines` = the registration paths the faculty offered the cohort per course (`[lecture]` or `[lecture, tutorial]` group numbers; physics is empty until its list is known). The cloud exports it in `build-static.js` and `gate.js` serves `/data/committee.json` to the owner alone (404 for anyone else); locally `/api/committee`. `client/src/lib/committee.js` derives all possible lines from a course's catalog groups (tutorial 21 belongs to lecture 2) and `occupancy` assumes the cohort splits evenly over a course's selected lines: a cell's busy share is 1 − Π(1 − share per course). Which lines count is stored in the owner's own progress (`progress.committee.lines`).

### Students' own files (`/files`, cloud only)

Every student can add lectures and tutorials for themselves ("הקבצים שלי", `client/src/pages/Files.jsx`; viewer `MyFile.jsx`; strip under a course's lessons/tutorials `components/MyFiles.jsx`): pick any site course (`/api/me/files/courses` lists all of them, `enrolled` marks the student's own), then lectures or tutorials. They are **private and never get AI** – no summary, questions or cards; those exist only for what comes from Moodle or what the owner adds himself on the Mac. `cloud/lib/files.js` keeps them in D1 (`user_files`, `user_file_chunks`; R2 isn't enabled on the account) as base64 chunks of 512 KB: the browser (`client/src/lib/personalFiles.js`) cuts, encodes, decodes and rebuilds the file, so the Function does no per-byte work. Limits in `LIMITS`: 20 MB a file, 100 MB and 60 files a student; types pdf/ppt/pptx/doc/docx (the type is set from the extension, never from the upload). A PDF is read with pdf.js from a blob URL, the rest are downloads. Chunk responses are `no-store` and the service worker skips `/api/me/files/<id>/chunks/` so another account on the same browser never sees them; sign-out clears the in-memory blobs. The files are deleted with the account (`deleteAccount`); they are not part of the published data, of `gate.js`, or of the weekly D1 backup (`/api/admin/backup` exports only users, progress and reports).

### Exam schedule (`/exams`, `client/src/pages/Exams.jsx`)

Every student sees their own courses' sittings (מועד א׳/ב׳ and quizzes, for their exam group, own dates replacing the official ones as in the prep page) on one timeline with days left, time and rooms, and a warning when two courses' sittings are within a day or two (`markNear` in `lib/examSchedule.js`). They are already in the cloud's calendar feed (`cloud/lib/ics.js`). The owner also gets "תצוגת ועד": per course the distinct dates across all exam groups and the gaps between consecutive courses' מועד א׳ and ב׳ (`overview`), including courses the site doesn't carry (linear algebra's `exams` live in `data/committee.json`, refreshed with its classes).

### Run log, AI output checks, weekly report

- **Run log** (`server/lib/runlog.js`): every process run is one JSON line in `logs/runs.jsonl` (`STUDY_RUNLOG` overrides) – process, trigger, start/end, input, output, status (`ok` / `checked` / `rejected` / `error`) and the checks' findings. `startRun(process, { trigger, input })` → `.ok(output, checks)` or `.fail(error, checks)`. Logged: lecture analysis, notes, syllabus grading, practice, homework practice, notices, Moodle sync, publish, weekly report. The local `/runs` page lists them and exports CSV (the project's documented-runs appendix). runlog.js must not import store.js (store → publish → runlog cycle).
- **Fixed checks after every AI step** (`server/lib/checks.js`): `checkLecture`, `checkNotes`, `checkQuiz`, `checkProblems`, `checkGrading`, `checkNotice` clean what a rule can fix (findings `fixed`/`warn`) and `assertUsable` throws `CheckError` on a `reject` (the output isn't saved; the item gets an `aiError`). Anything new that saves model output should go through one of them.
- **Weekly load report** (`server/lib/weekly.js`): Sunday from 07:00 (checked hourly) or `POST /api/weekly/run`; covers the 7 days from the day it's made. Dates, counts and load points are deterministic (`shared/weekly-load.js`); the AI writes only a headline and per-course advice, checked by `checkWeeklyText` (no course names or digits in the headline, known courses and dates only) with fixed fallbacks. Saved to `data/weekly/<date>.json` (published), announced as a `report` feed item (cloud push rule 8). In the cloud `/data/weekly.json` is filtered per student by `forCourses` in `cloud/gate.js`. Personal state (submitted or not) must stay out of it – the report is shared.
- **`docs/runbook.md`**: the Hebrew operating instructions for someone who didn't build it (mock Moodle, `STUDY_DATA_DIR`, no cloud), kept in step with these processes.

### AI (`server/lib/ai.js`)

`generateJSON` (structured output against a JSON schema) and `chatStream` (SSE to the client via `/api/chat`). Provider is `api` (Anthropic SDK, needs `ANTHROPIC_API_KEY`), `cli` (spawns the local `claude` binary headless with no tools/settings, using the owner's login) — `cli` is the default when no key is set — or `gemini` (`AI_PROVIDER=gemini` + `GEMINI_API_KEY`, `server/lib/gemini.js`, SDK `@google/genai`). With Gemini the lecture and notes calls also attach the deck's PDF (`deckPdf` in ingest.js; inline up to 18 MB, File API above, 50 MB max), Gemini reads its pages as images, and the prompts add `DECK_PDF_RULES` (extract every number, definition and example) and `DECK_PDF_QUIZ` (40–80 questions in the same call). Free-tier limits are enforced locally: one call at a time spaced to `GEMINI_RPM`, a per-Pacific-day count against `GEMINI_RPD` (default 20 – Google's free-tier limit per project per model for flash; a "per day" 429 from Google marks the day used up) (`logs/gemini-usage.json`), low-priority calls (question banks) stop at `1 - GEMINI_RESERVE` of it, and a used-up day or Google's 429 surfaces as a usage-limit error that the AI watch waits out. Every `generateJSON` answer is cached by its full request – provider, model, system, prompt, schema and the sha256 of attached files (`server/lib/ai-cache.js`, `cache/ai/`, gitignored) – so the same deck is never sent twice; `cache: false` (regenerate) skips it. **Lessons vs everything else:** `AI_LESSONS=claude` (with `AI_PROVIDER=gemini`) sends the lesson material – the lecture/tutorial/homework analysis (summary, topics, glossary, flashcards, the lesson's first questions) and the structured notes – to Claude (`AI_LESSON_MODEL`, default Sonnet, 12-minute call limit) and falls back to Gemini when Claude fails (timeout, usage limit, signed out, an output the checks reject): `generateLesson({ build(by), check })` in `ai.js`, `lessonRoute()` / `lessonsReady()` say who is tried. Gemini gets the deck PDF and the bigger first question set (`DECK_PDF_*`), Claude the text. Question banks, extra practice, syllabus, weekly report and chat stay on `AI_PROVIDER` (Gemini), so the free-tier quota (`GEMINI_RPD`, 20 a day for flash) goes to the banks (`GEMINI_RESERVE` keeps a few for the fallback). `checkAI` also probes Claude (`probeClaude`, `aiWatch.claude`) and retries failed lessons when either answers. The saved `content.generator` says who wrote it. All prompts and schemas live in `server/lib/prompts.js`. AI is unavailable in the cloud build.

A dropped internet connection on the Mac (every call "fetch failed") is treated as a blip, not an outage: the AI watch looks again after 3 minutes and alerts only after three misses (`isNetworkError`, `checkAI`), and a Moodle sync whose errors are all network errors is retried after 3 minutes and shows as a problem only when the next one fails the same way (`state.netFails`).

### Auto-publish (`server/lib/publish.js`)

Every store write of published data calls `schedulePublish(label)`. After 2 quiet minutes (and once nothing is processing) the server commits **only** the data paths (`data/lectures`, `data/courses.json`, `data/practice`, `data/updates.json`, `data/links`), runs `git pull --rebase --autostash`, and pushes to `origin` — which redeploys Cloudflare. Code changes in the working tree are left alone, but expect these commits to appear on `main` while the server runs; set `AUTO_PUBLISH=0` when experimenting with data.

### Moodle and the admin channel (`server/lib/moodle.js`)

Uses the Moodle mobile web-service API. The Mac syncs its own courses with its token, and syncs other students' courses through the cloud's `/api/admin/moodle` proxy (`remoteRest`), so students' tokens never leave Cloudflare. That requires `CLOUD_URL` and a `STUDY_ADMIN_SECRET` of at least 32 chars matching the cloud's `ADMIN_SECRET`. Weekly backups of the D1 data come through `/api/admin/backup` (`server/lib/backup.js`); restore with `scripts/restore-backup.js` → `wrangler d1 execute study-hub --remote --file …`.

### Phone notifications (cloud only)

Web Push is implemented with plain WebCrypto in `cloud/lib/webpush.js` (VAPID + aes128gcm); `cloud/lib/notify.js` decides what is due (deadlines, exam tomorrow, due flashcards, class in 15 minutes, room change of the student's group) and dedupes via the `push_sent` table. Pages Functions have no cron, so a separate Cloudflare Worker (`workers/push-cron`, deployed with `npm run deploy:cron`, secret `ADMIN_SECRET`) POSTs `/api/admin/push/tick` every 5 minutes. The Mac's `server/lib/push-tick.js` ticks too as a backup (`{ backup: true }`); the cloud skips those while the Worker has ticked in the last 8 minutes (`push_meta` table), so the two never race. Keys: `VAPID_PUBLIC_KEY` in `wrangler.toml`, `VAPID_PRIVATE_KEY` as a Pages secret (generate with `node scripts/vapid-keys.js`). Students' per-kind preferences live in their progress blob (`progress.notify`). News about the courses (new material, announcements, class changes, portal notices, the weekly report) is pushed at any hour; only reminders (deadlines, a lapsed Moodle sign-in) wait for 08:00–22:00. The owner (the degree committee) also hears at once about every connected student's portal notices – each notice once, with no student named – both as pushes (`otherPortal` in `dueNotifications`, not held for Claude's reading) and in their updates feed (`portalFeed` with `owner`); their own portal link is read every 5 minutes, the others' every 15 (`STALE*` in `portal.js`), and Moodle courses are looked at every ~4 minutes. The portal connect form tells students that such notices may show to the site's owner. The owner follows only the cohort's groups – the registration lines the faculty offered (`lines` in `data/committee.json`, turned into `{ course: { type: [groups] } }` by `cohortGroups` in `shared/groups.js`; `forOtherGroups` takes lists of groups): announcements, class changes and other students' portal notices (`lessonInCohort`) about other groups are neither pushed nor shown on the updates page (a toggle shows them), and the owner gets announcements and class changes of the cohort's groups of every course (`owner` in `dueNotifications`; the updates page doesn't hide other groups from them either), students only their own group's.

The tick also watches Moodle without the Mac (`cloud/lib/moodle-watch.js`): a few courses per tick, each about every 10 minutes, through the token of an enrolled student (`asCourseMember`). It lists new files (classified by `shared/moodle-kind.js`, shared with the Mac's ingest) and news-forum posts into `cloud_updates`; the first look at a course only records a baseline in `moodle_watch`. `mergeUpdates` folds these into the feed (`gate.js`) and notifications, dropping any the Mac already has by `key` (`announcement:<discussion>`) or `fileKey` (`<moodleId>:<cmid>:<path><name>`, stored in the lecture's `source.fileKey`). Cloud file notices wait 30 minutes so a running Mac can get there first; when the Mac's item for an already-announced file arrives, it is sent as "מוכן באתר". A student whose Moodle token expired (`token_ok = 0`) gets a weekly "reconnect" notification and a banner on the site.

### System status (owner only)

`/system` shows whether each moving part ran lately: the cron Worker, the Moodle watcher (per-course errors in the `health` table, `watch:<moodleId>`), the portal readers (`portal_relay:<source>` in `push_meta`), the Mac and its publishing, new files waiting for a summary, and students' connections. The checks are built in `cloud/lib/health.js`; the Mac's part comes from a heartbeat (`server/lib/health.js` `macHealth`) sent with every Mac tick and stored as `health` row `mac`, and its checks are in `shared/system-checks.js` (also used locally when the cloud doesn't answer). The owner is the Moodle user the Mac is signed in as (sent in the heartbeat, `push_meta` key `owner`); only that user gets `owner: true` from `/api/me` and can read `/api/system`. The owner also sees every site course in the cloud – feed, new-material/announcement notifications and the material itself (`visibleCourseIds` in `cloud/lib/account.js`, used by `gate.js` and `notify.js` as `feedCourses`); courses they aren't enrolled in come back from `/data/courses.json` with `other: true` and are listed under "קורסים של סטודנטים אחרים". Everyone else sees only their enrolled courses (`allowedCourseIds`). On the Mac, `/api/system` posts a fresh heartbeat to `/api/admin/system` and returns the cloud's answer. Two checks guard against quiet failures: **Claude on the Mac** – `checkAI` (`server/lib/health.js`) runs `probeAI` (a tiny request on the smallest model) every 30 minutes, reports `aiWatch` in the heartbeat (signed out / limit / error → alert), and when Claude answers it calls `retryFailedAI({ auto: true })` (`ingest.js`: items with `aiError`/`notesError`, at most `AUTO_RETRIES` per item via `meta.aiRetries`, reset on success; the manual `POST /api/maintenance/retry-ai` has no cap); and **the cloud deploy** – the heartbeat carries the Mac's `origin/main` commit (`git`), and `cloud/lib/health.js` compares it with the live `data/build.json`, alerting when the site is still on an older build 30 minutes later (a failed Cloudflare build leaves the old site up without telling anyone). Each tick turns a check's `alerts` into phone notifications to the owner (08:00–23:00, keyed `health:<key>:<date>` so at most once a day each, or once ever with `once`). For local cloud testing, the `mock-moodle` and `cloud-dev` (`wrangler pages dev`) launch configs work together (`.dev.vars` points `MOODLE_URL` at the mock).

### BGU student portal (each student's real groups and room changes)

The portal (portal.bgu.ac.il) is the only per-student source of groups and timetable — Moodle has neither (no groups in academic courses, merged "01" course codes, no timetable events). Its firewall (AWS CloudFront geo-restriction) answers only from Israel — even a Cloudflare Worker placed near Tel Aviv is blocked — so a reader in Israel does it: an always-on machine running `relay/run.mjs` — an **old Android phone at home** (Termux service, installed over SSH with `./scripts/deploy-portal-android.sh <phone-ip>`) or a VM in Israel (`./scripts/deploy-portal-vm.sh ubuntu@<ip>`); both scripts first check that the portal answers from there — with the **Mac** as backup (`server/lib/portal-relay.js` asks with `&backup=1` and gets nothing while any other reader was seen in the last 3 minutes). Cloud options tried and dropped: a Cloudflare Worker (blocked even when placed near Tel Aviv), AWS Lambda in il-central-1 (the AWS "Projects" account can't opt in to regions), Oracle Cloud (sign-in trouble). Both run `shared/portal-relay-core.js`: poll `/api/admin/portal/jobs`, sign in only when the stored portal session (encrypted by the reader with a key derived from the private key, kept opaque in `portal_state`) has ended (`shared/portal-api.js`: `StandardLogin` → bearer token + the cookies it sets → `umbraco/Surface/MainPortalSurface/GetPageData` with `pageUrl: 'academy/schedule-and-courses'` → the `StudentCoursesAndScheduleBlockList` block's `scheduleByDays`; `Portal/Api/Home/Index` is only the home page), and posts the lessons to `/api/admin/portal/result`. The student's sign-in (username, password, ID) is sealed in their browser with the Mac's RSA-OAEP public key (`PORTAL_PUBLIC_KEY` in `wrangler.toml`; private key in `portal-key.json`, created by `node scripts/portal-key.js`, not in git, and copied to the reader machine) — the cloud stores it in `portal_links` but can't open it. A failed sign-in sets `ok = 0` and is never retried. The cloud derives the student's groups from the lessons (`shared/groups.js` `groupsFromPortal`: day/time, then room numbers, then BGU numbering — tutorial 21 belongs to lecture 2); those groups override hand-picked ones in notifications, and the timetable page copies them into `progress.classGroups`. The student's own portal notices also join their updates feed in the cloud: `gate.js` adds `portalFeed` (`portal.js`) to `/data/updates.json` – items of type `portal`, keyed `portal:<noticeKey>`, last 30 days, with Claude's reading and the course found by `courseOfLesson` (`shared/groups.js`: name or code, else the one course with a catalog meeting of that kind at that day and time). They are built per request from that student's `portal_links` row and never published, so no one sees another student's notices. `forOtherGroups` (same file) drops course announcements aimed at other groups, both from phone notifications and (hidden by default) from the updates feed. A portal lesson is matched to a site course by a telling word of its name (`sameCourse` in `shared/groups.js` ignores words many names share – מבוא, יסודות, להנדסה… – after "מבוא לפיזיקה" was taken for "מבוא לכלכלה"), its code, or its day and time. Courses the catalog lists without meeting times (physics: only group numbers) can't get a group from the portal; their lessons still show on the timetable as the portal has them (`portalOnlySlots` in `client/src/lib/schedule.js`, no group). A student who hasn't connected the portal picks groups by hand – the connect card sits at the top of the timetable. A wrong portal password must not return HTTP 401 — the client treats 401 as "signed out of this site". Local tests: `mock-portal` launch config, `PORTAL_URL` in `.dev.vars`, and a relay run with `CLOUD_URL=http://localhost:8788`.

### Client notes

- Flashcards use Anki-style SM-2 scheduling in `client/src/lib/srs.js`; old Leitner cards (`{box, due}`) are converted on read, and `box` is still written because `lib/exam.js` and `Home.jsx` count it.
- The deck a student sees is built by `deckOf` in `client/src/lib/cards.js`: AI cards keep the key of their original question even when edited (`progress.cardEdits`), hidden ones are dropped (`cardHidden`), and the student's own cards (`customCards`) are keyed `${lectureId}:c-${id}`. Anything that looks up a card's progress must go through these keys.
- `progress` is one blob saved whole on every change: anything that writes automatically (timers, effects) must wait for `progressLoaded`, or it overwrites the saved progress with the empty default.

- **`/guide` ("איך משתמשים", `client/src/pages/Guide.jsx`)** explains each part of the site – install on a phone/iPad, the home page, updates and notifications, connecting the timetable to the portal (`/guide#portal`, linked from the portal card), the timetable, exam schedule, course and lesson tabs, review, grades, weekly report, search/timer, archive, privacy; entries marked `owner` (the committee page, system status) show only to the owner. Keep it in step when a feature changes. The first-sign-in tour (`Onboarding.jsx`) ends with a step that opens it.
- The unread badge (`unread` in `store.jsx`) counts only what the updates page shows: `isOtherGroups` (`lib/otherGroups.js`, also used by `Updates.jsx`) removes news about other groups (for the owner: other than the cohort's), so the bell never shows a number for items hidden behind "הצגת הודעות לקבוצות אחרות".
- `client/src/store.jsx` holds app-wide state (signed-in student in the cloud, progress with Leitner flashcard scheduling, courses, updates, toasts). Progress is one JSON blob: `PUT /api/progress` locally, per-user D1 row in the cloud.
- Interactive per-course "labs" are registered in `client/src/labs/index.js`.
- `client/public/sw.js` is a service worker; `_headers` (written by `build-static.js`) sets it to `no-cache`.
