# Notices read by Claude (`server/lib/notices.js`)

The course material goes to whatever `AI_PROVIDER` says (Gemini by default now), but every new **notice** is read by Claude (`generateJSON({ use: 'claude' })` → `claudeStatus()`: the API key or the logged-in CLI, model `NOTICES_MODEL`, default `claude-sonnet-5-5`, effort low): Moodle course announcements on the feed (`pendingNotices` / `setNoticeAnalysis` in `updates.js`, last 14 days, 3 tries each) and the portal's notices on students' lessons (`GET /api/admin/notices/pending` → `POST /api/admin/notices/result`; the cloud keeps them in `notice_analysis` by `noticeKey`, deduplicated across students, a NULL row's `at` counts failed tries). The reading (`NOTICE_SCHEMA`: kind, groups, room/day/time/date, headline, urgent) passes `checkNotice` – groups must exist in the course's catalog classes, room/time/date/headline may not carry digits the notice doesn't have, `urgent` only for lesson changes. It runs after every Moodle sync and every 3 minutes (cheap when nothing is waiting: no run is logged; `startNotices`, `NOTICES=0` off; `POST /api/maintenance/notices`), logged as run process `notices`. The cloud holds a portal notice's phone push for up to 10 minutes while it is unread and the Mac's heartbeat is recent (`heldNotices` in `portal.js`, first sight in `push_meta` as `ns:<key>`), so it usually goes out with Claude's headline; after 10 minutes, or when the Mac is off, it goes out in the portal's own words. `shared/notices.js` is how it's used: `forOtherGroups(text, course, mine, analysis)` trusts the reading's groups over the text heuristics, notifications (rules 6 and 7 in `notify.js`) take `noticeTitle` as the title and `noticeUrgent` as a high-priority push, `portal.js` attaches readings to the lessons (`withReadings`), and the updates page / portal card show the kind and headline. A reading (version `NOTICE_VERSION`, older ones are read again) also says which meeting it is about – `classType`, `onDate` (YYYY-MM-DD, worked out from the posting date and verified by `checkNotice`: within -10…+60 days, on the weekday and the date the text names), `repeats` (permanent), `start`/`end`. **`shared/schedule-changes.js`** turns cancellations, room changes and time changes into dated changes (`changesFrom`, `changeFor`): the site's timetable (`slotOn` / `thisWeek` / `upcoming` in `client/src/lib/schedule.js`) marks a cancelled meeting "לא מתקיים" (and shows the new room or time) until that meeting has ended, then it is the regular one again; a permanent change stays for later weeks. A permanent change that names only a weekday ("בימי ראשון … שינוי קבוע") has no `onDate`: `checkNotice` keeps `repeats` when the day is named (and sets it from wording like "שינוי קבוע" that the model missed), and `changeOf` starts it at the first such weekday from the posting date. `NOTICE_VERSION` = 3. A portal notice is anchored to its own lesson (weekday + start; no date → the lesson's next meeting after it was posted), an announcement matches by course, class type, groups, weekday and start. The cloud's class reminders (rule 4) use the same changes. The portal's own `canceled` flag counts for this week's meeting only. Without a reading everything works as before on the plain text. The `/system` page has a `notices` check from the heartbeat (`noticesState`).
